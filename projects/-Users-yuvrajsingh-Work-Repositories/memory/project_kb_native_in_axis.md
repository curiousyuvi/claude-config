Yuvraj + team are evaluating **rebuilding the InstantDocs Knowledge Base entirely inside Axis from scratch** (instead of the current SSO/IDP join — see [[project_kb_in_sidebar]]). Phase 1 = basic KB (collections, articles, rich-text + custom blocks, published public site, fast+fuzzy search, caching, custom-domain hosting, AND all theme/layout/customization). Phase 2 = video (recording, Remotion render, timeline editor, ElevenLabs AI voiceover sync). **Explicitly out of scope: Knowledge Gap and Analytics.**

**Yuvraj's committed timeline: ~1 month per phase (Phase 1 KB, Phase 2 video), back to back.** He rejected my conservative bottom-up estimate — rightly: he is the sole author of all InstantDocs code, most of it ports rather than gets rebuilt, Axis already has the hard infra (BullMQ/outbox/Ably/Qdrant/storage/kb.schema/reader UI), and agentic coding compresses the mechanical volume. The framing is **port proven code onto Axis primitives, not rebuild**. Team-facing scope doc (human-voiced, no AI fingerprints) saved at `~/Desktop/Axis KB Migration - Scope & Plan.md` with 4-week week-by-week milestones per phase.

The only genuinely new-on-Axis pieces (where schedule risk concentrates): the public SEO site (materialize HTML→S3+CDN) and custom-domain TLS in P1, and voiceover-video sync in P2. Everything else is lift-and-shift.

**Scope guardrails (per Yuvraj, this is a spike):** NO migration of existing InstantDocs users/data into the new KB — build fresh; existing tenants stay on InstantDocs for now. Don't raise migration/cutover as a concern. Explicit "fix from the start" items: split KB god-table; proper Postgres tree + one OrderingService; one outbox event for all side effects (no SFN for publishing/jobs); zero-downtime Typesense reindexing + disciplined reconcile for Qdrant/caches; editor architected for future real-time collaboration (CRDT/Yjs); durable BullMQ jobs; compliance-ready by design. Do NOT mention private-KB password hashing in docs.

**Key findings to remember:**
- Axis ALREADY has: BullMQ Pro + FlowProducerPro + transactional outbox (replaces InstantDocs' AWS Step Functions cleanly — user's "better workers" intuition confirmed); the full RAG/Qdrant ingestion stack; **Ably realtime** (so presence/edit-lock transport is NOT greenfield); S3 storage; the `kb.schema.ts` wire contract; and a host-agnostic KB reader UI in `apps/web/src/features/knowledge`.
- The two hard greenfield gaps: (1) **public SEO/custom-domain site** — Axis web is a `noindex` Vite SPA that can't SSR (recommend publish-time materialize HTML→S3+CDN); (2) **video pipeline** — zero video infra in Axis.
- Biggest up-front decisions: public-site serving model, KB ownership/migration posture, tree representation (closure table), i18n shape (symmetric variant rows), custom-domain TLS (recommend Cloudflare for SaaS), search engine, editor (DECIDED: Plate.js — see below).

**EDITOR DECISION (2026-06-24, after research — FINAL): Plate.js (Slate).** History: BlockNote rejected (custom blocks capped at inline/none content — the root of InstantDocs' inner-editor + stringified-JSON-in-props hack for accordion/steps/updates/callout). Briefly leaned TipTap, then **reversed to Plate** after calibrating the two knocks: (a) collab — Plate's `@platejs/yjs` syncs nested *content* fine (one shared doc tree); the dormant `slate-yjs` binding only means owning a few papercuts when collab is enabled (deferred), and the "nested doesn't sync" caveat is about embedded sub-editors, which good design avoids; (b) large-doc perf — Slate re-renders broadly but is fine at KB article sizes (3k words ≈ a few hundred nodes; pain threshold ~7k+ words/thousands of nodes, rare for help docs) and published pages are static (zero editor cost for readers). Plate wins on DX + batteries: shadcn UI copied into the repo (MIT, matches Axis), ergonomic custom-block API, and NO nesting ceiling (custom blocks = Slate elements whose `children` are real nested blocks). Content stored as **Slate JSON** (recursive node tree) in jsonb; semantic HTML/MD via `serializeHtml` / `PlateStatic` (RSC) / `@platejs/markdown` (server+client). Plate is a NEW dep added to the SPA (coexists with the ticket composer's existing TipTap). Mitigations: pin Plate+Slate to exact versions behind an editor adapter; Slate chunking only if an article gets very long; rebuild editor state/lifecycle clean (no force-remount). Both Notion docs updated to reflect Plate.
