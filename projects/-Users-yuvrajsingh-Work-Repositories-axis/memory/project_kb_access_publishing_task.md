Notion spec: https://app.notion.com/p/397b7d82b70780f79d85f48d453e9cd6 (Helply Roadmap). Scope agreed 2026-08-11: KB-level access modes (adds an "Authenticated" rules mode to the existing public/password/members trio), article-level access (Public / Company-Contact via filters / Internal), enforcement on every surface. **Review & Publish (spec §6-9) is NOT being built now.** Page comment: the assignee planned two tasks — Privacy (KB & Article) first, Review & Publish later; also an open question about where IP whitelisting sits in the new settings UI.

Key current-state facts the plan rests on (verified by exploration 2026-08-11):
- KB-level gating already exists end to end: `KbAccessGate` (exclusive modes via `kb_access_gates_one_access_mode` CHECK, IP allowlist stacks), edge gates in `apps/kb-edge/src/gates.ts`, origin `kb-reader-gate.handler.ts`, member auth = Better Auth session → HMAC `kb_member` cookie (`shared/kb-member-token.ts`), `KbGuest` invited emails, gate change → KB_UPDATED → full rebake + purge.
- NO per-article access concept exists anywhere (Article entity has only status). Nav/prev-next/breadcrumbs are embedded in every baked page, so per-article visibility changes are full-KB rebakes; per-audience nav requires origin rendering.
- `kb_published` OpenSearch index has no access field; `/_kb/search.json` is never edge-cached (origin every request) so per-visitor filtering is feasible there.
- There is NO end-customer (contact) authentication anywhere in the product — no portal, no magic link, no widget identity. Building contact login is the biggest new subsystem in this task.
- Contact/company view filters (`ContactViewFilters`, select+date kinds) are stored opaque and evaluated only client-side into query params; a server-side `matches(filter, contact) => boolean` evaluator does not exist and must be written (recommended: SQL `WHERE id = :x AND <clauses>` reusing the list-endpoint Kysely clause builders).
- Leak paths found: `/kb-assets/:id` is org-unscoped capability URLs (assets also live on the public CDN, see [[kb-asset-cdn-unsigned-urls]]); `KbNodeMetaService` resolves any published article's title org-wide (connected cards).
- Chosen serving shape: bake/cache only the anonymous-public variant; any request carrying a KB identity cookie routes to origin for personalized render (`private, max-age=0`). Restricted article pages are not baked at all.
- Hard prerequisite: the bake-reap fix ([[project_kb_bake_never_deletes_orphans]], branch `ys/feat/kb-edge-static-surface`) must be merged first, or a newly-restricted article's stale baked page keeps serving publicly.

**DECIDED 2026-08-11 (Yuvraj), the 8 plan questions:** (1) contact login = 6-digit email code; (2) workspace members see ALL articles incl. company/contact-restricted; (3) article-level access exists ONLY when KB mode = link-public (the spec self-contradicts in §4; resolved to link-public only); (4) assets stay unguessable-URL-protected, no signing; (5) embeds serve public articles only; (6) the SAME KB+article privacy applies to agents in the inbox KB panel (no agent bypass — KB-level authenticated rules evaluated against the agent; article-level collapses to "members see all" per decision 2); (7) origin-rendered uncached pages for identified visitors accepted; (8) rule UI reuses the standard contact/company filter system.

**DECIDED 2026-08-11 (Yuvraj), round 2:** article privacy strictly link-public-only (reconfirmed); AI retrieval policy = restricted (audience/internal) articles excluded from customer-facing AI retrieval, agent-facing copilot follows the inbox-panel KB rules (+ GraphRAG re-tag backfill); inbox panel corner case = org admins ALWAYS see an authenticated-mode KB even when its rules have no member arm. Custom-field filters: Option A chosen (v1 rules use existing filter fields + explicit company/contact picks; custom-field filtering is a separate follow-up task, NOT built here). ALL decisions now closed; work order written to repo-root `KB-ACCESS-PRIVACY-HANDOFF.md`. **DECIDED 2026-08-11 (Yuvraj): drop KbGuest entirely BEFORE starting the Notion task.** All of it — `kb-guest.entity.ts`, the guest methods on `KbAccessGateService` + controller/DTOs, `isActiveGuest` in `KbAuthorizeService`, the never-rendered frontend API layer (client/mutations/query-options/query-keys guest entries; the Share dialog Invite tab is only a `KbComingSoon` placeholder), the `kb_guests` table via migration, and any worker/spec references. Rationale: it was half-shipped (backend enforceable, zero UI), the spec's "Contacts" rules cover the same intent, and the privacy feature is complex enough without a parallel external-viewer mechanism. This is a standalone cleanup PR that precedes slice 1.
