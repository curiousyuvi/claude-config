Editor-header Eye button → new tab showing the article's CURRENT DRAFT rendered through the exact published reader chrome + an amber "This is a preview of your draft. Publish to make these changes live." banner. Ported from instantdocs' `/preview-draft/*` flow. Branch `ys/feat/kb-article-prepublish-preview`.

**Architecture:** served from an AUTHENTICATED app-origin route, NOT the public reader host. The public reader (`kb-public`) is a Fastify onRequest hook on KB subdomains serving PUBLISHED snapshots only (no session). Draft is admin-only, so the route lives in `KnowledgeBaseModule` under the global `BetterAuthGuard` + `@OrgId()`: `GET /api/knowledge-base/kbs/:kbId/articles/:id/preview?locale=` → `text/html`.

**Backend seam (reuse, don't fork):**
- `ArticlePreviewService.renderDraftPreview` mirrors `ArticlePublishingService.publish`'s render step — `linkResolver.resolve(em,orgId,kb,locale,variant.content)` then `PlateHtmlRenderer.render(resolved)` — but persists NOTHING (draft self/cross links to unpublished targets resolve inert = honest preview). Reads DRAFT fields (`variant.title/description/content`, `article.iconType/iconValue`), not `published*`.
- New `KbReaderService.previewDocView(kb, article, locale, body)` assembles a `ReaderDocView` around a caller-supplied draft body; chrome (tree/breadcrumb/prev-next) comes from the PUBLISHED tree (unpublished article ⇒ empty breadcrumb, null neighbours — acceptable). Fills connected cards like `doc()`.
- `KbPageRenderer.render(view, {origin, indexable:false, preview:true})`. `origin = kbPublishedOrigin(kb.slugNorm, config kbPublic.publishedDomain/protocol)` (there is NO `kb.publishedUrl` entity field; that DTO field is computed in the mapper).
- `RenderContext.preview` flag threaded into `kb-reader-jsx.tsx` `HtmlShell` (banner as first body child + `kb-preview` body class) + all 3 `Document` branches; owner custom head/body code is SKIPPED in preview (would run in app origin = self-XSS; also no analytics/chat noise).
- NO `<base>` tag (tried it, REVERTED): the reader host isn't reachable from the app/api origin in the sandbox, so `<base href={readerHost}>` broke every relative URL — notably the KB logo (`Logo` uses `kb.logoUrl` as `src` WITHOUT normalizeUrl; if stored relative it repointed to the dead host). Without base, absolute kb-asset URLs (`{apiBase}/api/kb-assets/{id}`) load, and relative ones resolve to the preview's own origin which serves them. Cost: in-KB nav links are relative-to-preview-origin (404 if clicked) — acceptable, a preview is for viewing not navigating. Banner component `PreviewBanner` in `kb-reader-chrome.tsx` + `EyeIcon` in `kb-reader-icons.tsx`; CSS `.kb-preview-banner` in `kb-reader.css` with `body.kb-preview.kb-body-doc` shrinking `.kb-doc/.kb-doc-inset/.kb-doc-sidebar` by `--kb-preview-h` (doc layout pins to 100vh, else banner clips).
- Wired export: added `KbPageRenderer` to `KbPublicModule` exports (`KbReaderService` was already exported; `KnowledgeBaseModule` already imports `KbPublicModule`).

**Frontend:** `kb-article-header.tsx` wires the pre-existing `<HeaderIcon label="Preview" icon={EyeIcon}>` placeholder — open `about:blank` synchronously (dodge popup blocker), await `onBeforePreview` (= `flushBeforePublish` autosave drain, passed from `kb-node-view.tsx`), then `tab.location.replace(url)`. Uses `activeLocale`.

**Clean URL via iframe (user-requested):** the Eye button opens an IN-APP route `/kb-preview/$kbId/$nodeId?locale=` (app origin, hides the API URL), NOT the API endpoint directly. Route file `apps/web/src/routes/kb-preview.$kbId.$nodeId.tsx` is TOP-LEVEL (sibling of `_authed`, NOT under it) so it renders full-screen with NO app shell (`_authed`→`AuthedRouteLayout` adds the whole nav shell). It renders `KbArticlePreview` (feature barrel) = a `fixed inset-0 size-full` `<iframe src={articlePreviewApiUrl(...)}>`. Both URL builders live in `features/knowledge-base/lib/preview-url.ts` (`articlePreviewRoutePath` + `articlePreviewApiUrl`). Adding the route needs a routeTree.gen.ts regen (boot `pnpm exec vite --port <free>` ~2s, it regenerates, kill it — see [[project_regen_tanstack_route_tree]]). `$nodeId` === article id (tree node id === article id).

**iframe framing (CRITICAL — do NOT use `src`+`frame-ancestors`):** app (`inbox.*`) framing api (`api.inbox.*`) via `<iframe src>` is CROSS-ORIGIN and `@fastify/helmet` sets `X-Frame-Options: SAMEORIGIN` → "api… refused to connect". A `frame-ancestors 'self' {appOrigin}` helmet-override was tried and FAILED because `kbPublic.appOrigin`/`FRONTEND_URL` defaults to `http://localhost:5173` in local dev (not the real `inbox.helply.localhost`), so it never matched. FINAL DESIGN: `KbArticlePreview` FETCHES the HTML (`fetchArticlePreviewHtml` — raw `fetch` returning `.text()`, `credentials:'include'`, the `.helply.localhost` cookie authorizes; `articlePreviewApiUrl` builds the URL) and renders `<iframe srcDoc={html}>`. srcDoc is SAME-ORIGIN ⇒ no X-Frame-Options/frame-ancestors at all, config-independent. NO backend middleware change (helmet untouched). Query: `articlePreviewHtmlQueryOptions` (staleTime/gcTime 0). In dev the relative logo (`/api/kb-assets/…`) resolves against the app origin and loads via Vite's `/api` proxy; body images are absolute api-origin URLs.

**Link-exit (srcDoc nav):** the reader's in-KB links (sidebar/breadcrumb/prev-next/cards/logo) are ROOT-RELATIVE reader paths; in srcDoc they'd resolve to the app origin and 404 ("Not Found"). `KbArticlePreview` intercepts clicks on the same-origin srcDoc doc (`onLoad` → `doc.addEventListener('click')`): for a `/`-relative (non-`//`) href it `window.location.href = new URL(href, kb.publishedUrl).href` — EXITS the preview and opens the LIVE published page in the tab. Fragment (`#`) + absolute/external links pass through. `publishedUrl` from `kbDetailQueryOptions`, read via a ref at click time (no query-order race). No published domain ⇒ guard no-ops. (Search form submit isn't intercepted — 404s in-frame; non-essential, known minor gap.)

**Sidebar active-highlight fix (reader-wide):** `kb-reader-chrome.tsx` `TreeList`/`containsActive`/`Sidebar` matched the active item by `slug`, but slugNorm is NOT unique-constrained, so two siblings sharing a slug both lit up (on the live reader too, not just preview). Switched to the unique `publicId` (`n.publicId === activePublicId`). `data-id={n.slug}` stays (localStorage key for sidebar-expand persistence). Goldens unchanged (fixtures match identically); 33 DB-backed kb-reader.service tests still green.

**Gotchas:** the whole `kb-reader.css` is inlined on EVERY reader page, so adding `.kb-preview-banner` rules churns all 12 golden snapshots (CSS-only diff, expected — re-run `-u`). Assert the banner ELEMENT via `class="kb-preview-banner"`, not the bare class name (the CSS selector matches everywhere).
