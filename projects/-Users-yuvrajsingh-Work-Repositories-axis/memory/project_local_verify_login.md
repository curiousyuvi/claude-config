For visual verification of UI work, the workflow is: **the user runs the local server, Claude logs in and verifies + screenshots**. This is the standard verification loop — always offer/do this instead of asking the user to check.

- App (dashboard): `https://inbox.helply.localhost` (Portless HTTPS; the KB reader is on `https://kb.helply.localhost`).
- Login: email `your-email@example.com`, password `password`. This is NOT a placeholder — it is the literal `SEED_AGENT_EMAIL` value set in `apps/backend/.env.local` (which overrides the `seed-agent@example.com` default in `apps/backend/src/database/factories/constants.ts`), so the seeded user's email really is `your-email@example.com`. Local test data — safe to create/edit/delete anything while testing.
- DB access: `docker exec -e PGPASSWORD=password axis-postgres psql -U username -d axis -tAc "…"` (docker-compose defaults DB_USER=username / DB_PASSWORD=password / DB_NAME=axis). Note KB article `status` enum values are lowercase (`published`), not `PUBLISHED`. For multi-statement/heredoc SQL you MUST add `-i` (`docker exec -i … psql … <<SQL`) — without `-i` docker discards stdin and the SQL silently no-ops. KB base table is `knowledge_bases` (not `kb_*`); its name/tagline live on the variant, not the base row (base row has `slug`, `org_id`, `default_locale`).
- Login form: `#email` + `#password` + button "Sign in"; after submit wait for the URL to leave `/sign-in` before navigating on (auth is an async fetch + client redirect). Playwright resolves from `node_modules/.pnpm/playwright@<v>/node_modules/playwright/index.js` (CJS — `import pw from '…'; const { chromium } = pw;`), since pnpm doesn't hoist a top-level `node_modules/playwright`.
- Drive it with Playwright (installed: `node_modules/.bin/playwright`, chromium cached). Launch chromium with `ignoreHTTPSErrors: true` (Portless uses a local CA at `~/.portless/ca.pem`; see [[project_portless_local_tls]]).
- Scrapling MCP only does navigate+screenshot (no click/type), so it can't drive the login form or interaction-triggered UI — use Playwright for anything interactive.
- Deep-link routes to skip clicks: `/kb/{kbId}/settings/supported-languages`, `/kb/{kbId}/settings/localization`, `/kb/{kbId}/{nodeId}?locale={loc}` (opens a variant), `?translate={loc}` (opens the translation sheet + auto-starts translation). Pull real ids from the `axis-postgres` docker container.
- **Deep-link auth caveat (verified 2026-07-15):** a hard `page.goto` STRAIGHT to a guarded deep link (e.g. `/kb/{id}/settings/advanced`) bounces to `/sign-in?redirect=…` — the route guard redirects on a cold load before the async better-auth session resolves. Reliable pattern: `goto('/')` FIRST, log in (fill `#email`/`#password`, click role button "Sign in"), wait until it lands on `/tickets` (authenticated). Auth is **cookie-based on the API host** — better-auth sets `sessionId` + `__Secure-better-auth.session_token` on `api.inbox.helply.localhost` (NOT localStorage, NOT the app host). Once those cookies exist, API calls carry them; then navigate. Logging in on the redirect-coupled `/sign-in?redirect=…` page was flaky (bounced back). KB settings route id: `/kb/{kbId}/settings/advanced`; the seeded login user (`your-email@example.com`) is in org `00000000-0000-7000-8000-000000000001`, which owns the seeded KBs (`rest`, `convious`).
- **Reader verification = served markup, not the live DOM:** DevTools **Elements** shows the post-JS DOM — our own `/_kb/analytics.js` bootstrap appends the gtag `<script>` at runtime, and browser extensions inject nodes (`chrome-extension://…`, dark-mode `<style>`/`<link>`, `cz-shortcut-listen` on body). So owner custom-head code looks "not last" in Elements even though it IS last before `</head>` in the response. Verify head/body ordering + injected scripts with **View Source / `curl -ks`**, never the Elements panel. See [[project_kb_reader_serves_stored_html]].
